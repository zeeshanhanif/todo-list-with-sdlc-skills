## What may and may not be recorded here (public repo)

This repo is **public**. The rule this run follows:

- **Never**: any secret value — DB passwords, `sb_secret_` keys, JWT secrets,
  connection strings containing a password, service-account keys. These live
  only in GitHub Actions secrets, entered by the user out-of-band.
- **Never**: the **billing account ID**. Not a credential, but no workflow needs
  it and it is a useful handle for social-engineering Cloud support.
- **In-repo, by decision**: GCP **project IDs** and deployer service-account
  emails. They are implied by the Artifact Registry paths the workflows need,
  and grant nothing without an IAM binding.
- **Actions variables, by user preference (2026-08-14)**: GCP project **numbers**
  (carried inside the WIF provider resource name) and **Supabase project refs**.
  Neither is a credential — the WIF provider is unusable without a GitHub OIDC
  token whose `assertion.repository` equals this repo, and the Supabase ref is
  public by construction (browsers connect to `https://<ref>.supabase.co`). They
  are kept out of the public repo so it does not enumerate the topology.
  **What protects the pipeline is the attribute condition plus the fact that no
  deploy workflow runs on `pull_request`** — not the secrecy of these names.

## Open notes / deviations

- Supabase Free allows **2 active projects per org** — staging + prod fits exactly.
  Free projects also **pause after 7 days idle** (staging will hit this first).
- GCP project-ID availability cannot be probed: `projects describe` returns the
  same permission error for "taken by another account" and "does not exist".
  Creation is the only test; on collision, append a short suffix and record the
  final IDs here.
- **BLOCKER (2026-08-13): GCP project quota exhausted.** `todo-list-staging-9fbb`
  created; `todo-list-prod-9fbb` refused — "you have exceeded your allotted
  project quota" at 35 active projects. Both original IDs (`todo-list-staging`,
  `todo-list-prod`) were already taken globally, hence the `9fbb` suffix.
  Verified against live docs: **soft-deleted projects keep counting for 30 days**,
  so deleting old projects does NOT free a slot quickly. Quota-increase requests
  run ~2 business days. Awaiting user decision on how to proceed for prod.
- **Prod reuses a pre-existing project** (`todolist-53139`, created 2017-01-08),
  chosen by the user when quota blocked a fresh one. Audited read-only before
  adoption and again after linking billing: 4 storage buckets with **0 objects**,
  App Engine app present but **0 services / 0 versions** (bare shell, location
  `us-central` — matches our Cloud Run region), Firestore / Compute / Cloud SQL
  APIs never enabled, no Cloud Run services. Firebase APIs from 2017 remain
  enabled and are left untouched; they do not interact with Cloud Run.
  **Naming asymmetry to know about:** environments are `todo-list-staging-9fbb`
  and `todolist-53139` — the prod ID is immutable and says nothing about "prod".
- **Two connection strings needed, not one** (live docs 2026-08-13): Cloud Run's
  short-lived connections want the Supavisor **transaction** pooler (port 6543),
  but `node-pg-migrate` takes session-scoped advisory locks, which transaction
  mode does not support. Migrations therefore run over the **session** pooler
  (port 5432) while app traffic uses 6543.
- **Supabase Free has NO automatic backups at all** (not merely "no PITR", as
  first stated to the user — corrected 2026-08-13). NFR-REL-002's RPO ≤ 1h is
  therefore unbounded out of the box. Phase 7 compensates with a scheduled
  `pg_dump` to GCS plus a real restore drill; this does not meet RPO ≤ 1h and
  will be recorded as such.
- **Supabase legacy keys deprecate end of 2026.** `SUPABASE_SERVICE_ROLE_KEY` is
  consumed as an opaque bearer string in one place
  (`supabase-realtime.publisher.ts:64-65`), so a modern `sb_secret_...` key drops
  in with no code change — to be confirmed empirically against the broadcast
  endpoint in Phase 6. `SUPABASE_JWT_SECRET` is *not* an API key and has no key
  replacement: the API mints its own HS256 JWT (`realtime-token.service.ts:62`)
  that Realtime must verify, per FEAT-019 technical-design D9. Satisfied by
  either the legacy JWT secret or a self-set HS256 shared signing key. An
  asymmetric-only project would require rewriting the minting service →
  **escalate to detailed-design as a FEAT-019 amendment, do not patch here.**
  Follow-up (cosmetic, code change, not done here): env var still named
  `SUPABASE_SERVICE_ROLE_KEY` while holding an `sb_secret_` value.
- **Scaffolding defect found at first apply (2026-08-14): reserved `PORT`.**
  `deploy/cloudrun-api.yaml` and `cloudrun-web.yaml` both set `PORT` as a
  container env var; Cloud Run **reserves** it and refuses the deploy —
  `ERROR: (gcloud.run.services.replace) spec.template.spec.containers[0].env:
  The following reserved env names were provided: PORT`. Cloud Run injects PORT
  matching `containerPort`, and both apps read `process.env.PORT`, so removing
  the explicit entries is behaviour-preserving. Verified against live docs that
  the only other reserved names are `K_SERVICE`, `K_REVISION`, `K_CONFIGURATION`
  (services) and `CLOUD_RUN_*` (jobs) — none of which our YAMLs set. This is
  exactly the class of error `docs/scaffold-notes.md` predicted when it recorded
  the Cloud Run YAML as "validated by inspection (no local gcloud validator
  available)". Handled as a trivial realization detail: fixed and recorded, not
  escalated.
- Candidate architecture amendments raised by this run (not made here):
  §7 never named a region; §8's "confirm the Supabase plan tier provides PITR + HA"
  prerequisite is confirmed **not** satisfied on Free tier.
